# Agent-CC 整系统评估方案

日期：2026-09-07。状态：实验设计，尚未执行正式测量。

文档整理：2026-09-16。本文件维护评估总规则：B0–B5 基线与消融、E1–E7 实验范围、统一指标、统计和复现要求。当前 benchmark 的入口、任务与专用计时见[Agent 场景实验补充](./Argus-EMAS-Agent场景实验设计与论文借鉴-2026-09-14.md)；正式运行前逐项核对[方案 Review](./评估方案Review-CCF-AB-2026-09-07.md)。文档分工与阅读顺序见[论文目录说明](./README.md)。本次整理文档职责与评测范围表述，不新增实验结果或改变研究主线。

## 1. 评估目标与范围

以 Node Attestation、Workload Attestation 和 OpenClaw–OpenViking 实际交互为已有整链基础，任务评测纳入 LoCoMo/OpenClaw 与独立的 τ²-bench 记忆适配，回答三个问题：提供了哪些安全与接入收益，付出多少性能和资源成本，故障时如何停止交付并恢复业务。下图展示 OpenClaw 路径；各调用端的具体接入方式按实际运行配置分别记录。

```text
OpenClaw 节点                            OpenViking TDVM
Node 准入 → SPIRE Agent                  TDX Node 准入 → SPIRE Agent
         ↓                                        ↓
实际 Gateway 的 Workload 准入            实际服务进程的 TDX Workload 准入
         ↓                                        ↓
客户端 SVID → Gateway/插件               服务 SVID → Helper → NGINX
         └──── mTLS、双方身份核对 ────────→ 身份授权 → OpenViking 业务权限
         ←──────── 上下文、业务结果 ────────────────┘
```

Workload 取证针对 OpenViking 实际进程，TLS 凭据由 Helper 交付给 NGINX 使用。Node Quote 绑定 proof key，Workload Quote 绑定运行属性，SVID 签发与使用依赖 SPIRE/凭据交付链。客户端的 Node/Workload 证明方式按实际配置记录；双端同级 TDX 实验需要两端都完成对应取证与验收。

威胁模型覆盖网络攻击、未授权工作负载在实际权限内的操作，以及 TDX 约定范围内的 TD 外攻击。TD 内核、Provider、SPIRE、启动/登记链及凭据/TLS 组件属于信任边界；管理者改配置、停止组件等单列为故障注入。普通 SVID 轮换与重新证明分开评估。

OpenClaw 路径使用真实 Gateway、安装的插件和 OpenViking；τ²-bench 路径使用真实任务执行器及通过受测入口访问 OpenViking 的记忆 adapter，不要求它经过 Gateway。Server 混合负载使用实际发压客户端，与 Agent 任务分别报告。各路径记录两端节点、实际进程、Entry/policy、证据年龄、证书持有者和网络位置；软件替身、真实 TDX 和实际业务结果分别标记。

实现依据：[Node 合同](../Argus-TDX-Node-Attestation-CN.md)、[Workload 合同](../Argus-OpenViking-NGINX-SPIFFE-Helper-Workload-Attestation-Workflow-CN.md)、[OpenClaw 接入手册](../../adapters/OpenClaw/spiffe_client/README.md)。

## 2. 优势对比与验证重点

重点验证以下收益，并同时记录合法请求的成功率和代价：

| 候选优势 | 验证方法 | 对应实验 |
|---|---|---|
| 从合法节点进一步约束实际服务实例 | 检查节点不合格、镜像/配置不符、PID/实例错配时，是否仍能取得身份或进入业务 | E1、E2 |
| 身份、实际入口和业务权限形成完整交互链 | 核对真实 Gateway 请求、双方身份、后端处理及上下文使用结果 | E1、E7 |
| 失效联动限制旧身份继续支持交互 | 测量实际数据交付窗口、任务损失及恢复；比较保留/移除联动的配置 | E4、E7 |
| 应用复用共同的证明与身份能力 | 用两种调用程序 × 两种服务验证接入量、核心改动与相同安全行为 | E6 |
| 准入成本在持续业务中得到摊销 | 在相同证据年龄和连接复用条件下，比较冷启动、稳定请求与完整任务成本 | E2、E3、E5、E7 |

主要比较对象及其已有能力如下。共同能力不计为本项目的新增优势。

| 比较对象 | 已有能力 | 本项目的比较重点 |
|---|---|---|
| [标准 SPIRE](https://spiffe.io/docs/latest/deploying/configuring/)及 [LADC TDX–SPIRE](https://doi.org/10.1145/3697090.3698036) | Node/Workload 身份、Unix/Docker 属性检查、SVID 更新；已有 TDX Node 集成 | 实际实例属性取证、外部策略评估、身份使用关系和故障联动的增量 |
| [Confidential Containers + Trustee](https://confidentialcontainers.org/docs/attestation/) | 证明后交付秘密；[Init-Data/agent policy](https://confidentialcontainers.org/docs/features/initdata/)可约束镜像及管理操作 | 与日常服务身份、实际通信及应用接入的结合方式 |
| [Gramine RA-TLS](https://gramine.readthedocs.io/en/stable/attestation.html) | Quote 与 TLS 公钥绑定 | 标准 SVID 的接入和运维收益，同时比较代理方案的信任边界 |
| [Certifier Framework](https://github.com/ccc-certifier-framework/certifier-framework-for-confidential-computing) | 多平台证明、策略与安全通道 | SPIFFE 生态复用、接入改动和生命周期成本 |
| [Full Trust Alchemist](https://www.comsys.rwth-aachen.de/publication/2025/2025_galanou_trust-alchemist/) | 运行属性取证和动态证明 | 同等威胁模型下，取证如何用于实际服务身份及失效处理 |

只有在可比配置上获得证据，才能提出相应优势。若强基线提供了相同安全效果，重点报告系统接入、维护或成本差异。

## 3. 对照与消融

### 3.1 整系统基线

| 编号 | 配置 | 用途 |
|---|---|---|
| B0 | 匹配普通 VM，同版本业务，直接 HTTP | 基础成本参照 |
| B1 | TDX VM，同版本业务，直接 HTTP | 分离 TDX 平台成本 |
| B2 | TDX + 相同 NGINX/TLS/精确身份授权，静态测试 CA 凭据 | 分离代理、TLS 与授权成本 |
| B3a | TDX Node + 最强适用 SPIRE 原生 Workload 检查 + 相同业务入口 | 已有机密节点与工作负载身份基线 |
| B3b | B3a + 同等实例属性的独立取证、策略、凭据发布与失效联动；不生成第二份 Workload Quote | 比较更简单的强组合方案 |
| B4 | B5 移除单个机制的受控消融 | 解释机制贡献 |
| B5 | 完整 Node + Workload + 两端身份交付 + 实际 OpenClaw/OpenViking | 整系统结果 |

B3b 通过与已准入节点关联的认证通道交付实际属性，并执行等价策略；不能接受请求体自报属性。比较时固定允许的属性和平台证据年龄；需要额外 Node 重新证明的成本计入基线。无法提供相同保证的部分单列。

B4 分别消融实例引用、取证前后复核、证据/策略关联、实际证书加载确认和失效停服；其它配置保持一致。存在机制依赖时，说明联合消融范围。

固定业务代码、数据、资源、TLS 算法、连接策略和业务权限。基线复用本项目代码时标记为组合基线，并公开补丁；第三方原型复现、组合基线与消融分别报告。跨 CPU/TEE 的文献数值仅用于参考。

### 3.2 Node × Workload 分解

四组使用匹配的 TDX 环境，先改变服务端准入并固定客户端配置：

| 配置 | Node 准入 | Workload 准入 |
|---|---|---|
| F00 | 已批准的非硬件证明准入 | 最强适用原生检查 |
| F10 | TDX Node | 与 F00 相同 |
| F01 | 与 F00 相同 | TDX Workload |
| F11 | TDX Node | TDX Workload |

比较 F10−F00、F11−F01 的 Node 增量，以及 F01−F00、F11−F10 的 Workload 增量。结合时间线分析共享资源、缓存和并行初始化的影响。这些组用于归因，安全保证不等价。

非硬件 Node 使用可审查的正常准入机制；Entry/parent 与各自合法身份匹配。当前固定 parent/profile 若限制 F01，先完成受控适配并公开补丁，否则标为未运行。客户端具备同等 TDX profile 后再做镜像实验。

## 4. Benchmark 与工作负载

| 工作负载 | 设置 | 判定方式 |
|---|---|---|
| W0 通信微基准 | 受同等证明保护的 HTTP 测试进程；响应 1 KiB/32 KiB/1 MiB；新连接与复用连接 | 请求 ID、长度、内容摘要正确，确实经过被测入口 |
| W1 上下文读写与 Server 混合负载 | OpenViking 实际接口；1,000/10,000 个约 4 KiB 合成对象读写；增加官方 Server 压测的检索、资源导入、session 写入及 commit 混合负载 | 唯一对象/session 标识、实际内容与状态；请求吞吐、成功吞吐和后台完成分别统计 |
| W2 完整 Agent 工作流 | OpenViking 已有的 LoCoMo/OpenClaw 与 τ²-bench 适配；真实任务、读取/检索、上下文使用及适用的 commit/archive | 实际 Agent 请求来源、OpenViking 结果及用户任务结果相互对应 |
| W3 异构接入 | 两种调用程序 × OpenViking 与第二种真实服务 | 四个组合均通过业务、安全和生命周期验证 |

W1 的比例是合成负载。所有配置使用相同数据快照、种子与请求序列，写入和索引状态在各轮之间恢复。W2 固定模型、prompt、上下文、token/重试预算；模型或 embedding 的时间和资源单列。

2026-09-14 的[Agent 场景实验补充](./Argus-EMAS-Agent场景实验设计与论文借鉴-2026-09-14.md)细化 W1/W2/W3 与 E3/E5/E6/E7：当前选取 τ²-bench、LoCoMo/OpenClaw 和 Server 混合负载，重点观察延迟、吞吐、并发及异常，同时检查任务效果与交付条件。诊断复测、其他数据集及更多运行时保留为候选；本方案的 B0–B5 与 E1–E7 不变。

平台辅助测试选取 [ConfBench](https://www.diag.uniroma1.it/~delia/papers/dsn25.pdf)或 [CVM-eval](https://github.com/TUM-DSE/CVM_eval)中与实际瓶颈相关的 CPU、内存、I/O 和证明项目。第二服务可使用 [DeathStarBench Hotel Reservation](https://github.com/delimitrou/DeathStarBench/tree/master/hotelReservation)；记录实际保护了哪些调用边。

## 5. 实验设计

E1–E5、E7 为必做；保留框架通用性主张时 E6 必做。整系统结果由 E7 给出，各组件实验解释原因。

### E1：准入安全与跨层交付

- **Node**：未批准平台/测量值、错误 proof key、重放/过期 challenge、错误 PoP、Quote 与 nonce/key 错配、错误 Node policy/EAR、Provider/QGS/Trustee 失败。分别观察 Node 接受、Agent SVID、后续 Workload 身份和实际业务结果。
- **Workload**：镜像/配置不符、错误 listener/PID/旧实例、取证期间目标变化、证据/策略错配、弱平行 Entry。检查身份实际交给谁、代理连接哪个后端、错误实例是否取得数据。
- **交互**：错误客户端/服务端身份、过期或移除凭据、origin/重定向/明文绕过、伪造身份头、正确工作负载身份但错误用户权限。分别观察客户端发送、NGINX 接收和后端执行。

按“Node→实例→证据→策略/Entry→凭据→代理/后端→业务权限”的关系生成用例。每个适用检查有单因素负例与合法配对控制；增加发布、reload、重启期间的可重复交错和随机调度测试。

首次未获准与先前获准后的失效分别运行；后者检查旧凭据/连接的实际行为。使用随机数据标记、独立接收记录和业务读回作为 oracle，并先验证 oracle 能发现有意放行的违规。

输出跨层结果表：每例记录权限、配置、证据等级、准入/身份/后端/数据结果及合法控制。真实 Quote、协议输入注入和软件替身分列。

### E2：Node、Workload 与整系统启动成本

| 子实验 | 起止事件 | 分阶段记录 |
|---|---|---|
| E2-N Node 准入 | 认证发起 → Agent 身份可用；另设包含 TDVM 启动的组 | challenge/PoP、Quote、Trustee、签发/交付 |
| E2-W Workload 准入 | 已准入节点上的目标登记/首次订阅 → 目标身份实际可用 | 实例检查/度量、Quote、策略评估、Entry、凭据发布/加载 |
| E2-S 首次可信任务 | 启动声明范围内的两端/整栈 → 首个真实 OpenClaw 任务完成 | 两端准入、客户端加载、NGINX 加载、请求、业务确认的关键路径 |
| E2-U 更新与重建 | 普通轮换、订阅重连、受控 Node 重新认证分别发起 → 新身份用于业务 | 新证明次数/年龄、加载/握手、任务暂停与恢复 |

区分两端全冷、仅客户端冷、仅服务端冷和已就绪后的首个会话。记录控制面是否预热、镜像/模型下载是否计入，以及 collateral/镜像缓存状态。成功、失败和重试均保留。

输出分阶段分布及完整时间线。两端可能并行，端到端时间直接测量，不能将阶段 P99 相加。

### E3：请求性能与饱和行为

先跑 W0，再跑 W1 回放。主矩阵为 B0/B1/B2/B3b/B5 × 四档相同绝对到达率：预实验 B3b 在指定 SLO 下容量的 0.25/0.50/0.90/1.10 倍。冻结后各组不自行降压；另测各自最大 SLO Goodput。

在 B3b/B5 的中等和近饱和负载下展开载荷、新连接/复用连接及轮换敏感性。闭环并发扫描 1/4/16/64 单列，开放负载控制到达率并记录实际并发。

记录计划发出、实际发出、完成、超时及排队时延，监测发压端余量。固定 TLS、连接寿命、重试、超时及会话恢复配置。[wrk2 的恒定到达率方法](https://github.com/giltene/wrk2)可供参考，实际工具需支持客户端证书和 SPIFFE 对端校验。

输出 P50/P95/P99、绝对/相对开销、Goodput、错误率和资源曲线。

Server 性能优先复用 OpenViking 的 `benchmark/custom/session_contention_benchmark.py`，展开纯检索、纯写入/commit、读写混合和突发负载。补充统计各接口完成请求数/秒、成功请求数/秒、后台任务完成数/秒、队列和排空时间；原脚本的总 QPS 含失败事件，不能单独作为有效吞吐。该脚本已有并发 worker，开放到达率实验需另行适配。详见补充方案第 3.3、5.3 节。

### E4：双端失效、业务中断与恢复

| 故障类别 | 注入情形 | 下游观察 |
|---|---|---|
| Node/TDVM | 两端分别重启、SPIRE Agent 停止、首次/重新认证失败 | 旧身份与任务行为、新实例准入、首个恢复任务 |
| 证明依赖 | Provider/QGS/Trustee 超时、Node/Workload policy 不通过 | 新节点、新实例与既有会话分别如何处理 |
| 客户端 | Gateway 替换、交付进程崩溃/冻结、租约/身份失效 | 实际插件是否停止发送、关闭连接并重新绑定实例 |
| 服务端 | OpenViking 替换、Helper 故障、NGINX reload/加载失败 | 后端对应、旧连接、最后数据交付与恢复 |
| 双端更新 | 客户端/服务端单独及重叠轮换、适用的 bundle 更新 | 实际证书代次、握手失败、任务损失、证明次数 |
| 网络/提交 | Broker 或业务链路阻断；提交前及执行后响应返回前断连 | 任务丢失、重复、已执行但未收到响应、结果未知与恢复读回 |

同时保留新建连接、旧连接上的新请求、已有流式响应。记录触发、检测、最后发送/接收、确认停止、恢复完成时间，并关联用户结果和后端状态。

预先规定在途请求排空、观测时长和探测间隔。观察期内仍可交互的窗口标为右删失；分别报告网络在途与服务端发送，文件删除/systemd 状态仅作为辅助证据。停止窗口与恢复分布是实测结果，观测最大值不作为无条件上界。

客户端租约和服务端停服分别测量。当前服务端冻结检测、远端策略更新及旧身份撤销的实际边界必须记录。中断写入按业务标识查询结果，不能无条件重试。

### E5：控制链容量与在线业务竞争

比较纯业务负载与三种混合负载：Node 加入/重新认证突发、Workload 新实例/订阅突发、两者同时突发。固定任务到达率，测准入排队/失败及 OpenClaw 任务、OpenViking 请求的尾延迟与 Goodput。

此处的“混合”指准入控制链与在线业务竞争；E3 的 Server 混合负载指检索、写入、commit 等业务操作竞争。先分别测量，再叠加比较，避免无法区分退化来源。

并发会话初始扫描 1/4/16/64；实际节点和实例数量按硬件逐步增加，直到 SLO 饱和或资源上限。分别记录 Node 数、Gateway 进程数、服务实例数、会话数、Entry 数和证明请求率。回放验证器请求仅属于部件容量测试。

资源分账覆盖两端 VM/TDVM、Provider、Trustee、SPIRE、凭据交付、Gateway/插件、NGINX/AuthZ、OpenViking 及必要后端。输出固定成本、每实例增量、混合负载增长曲线及瓶颈；模型调用单列。

### E6：应用接入与复用

构建两种调用程序 × 两种服务的四格矩阵，例如 OpenClaw 与 Go 客户端分别访问 OpenViking 和第二服务。每格完成业务、同等准入及 E1/E4 的适用验证。

普通 Go 客户端只支持跨语言通信与接入结论。要进一步主张跨 Agent 运行时复用，第二调用方应运行真实的模型—工具—反馈循环，例如基于 LangGraph 的 Agent，并在相同任务族中复验；不能把两种调用程序或两个运行时直接算成 A2A 协作。

统计应用、适配器、核心的代码改动，以及配置、部署步骤和接入工时；排除生成代码与无关格式化。作者工时作为案例记录。原生 SDK 路径需先完成同等证明适配；仅测试 Helper 模式时，复用结论限定在该模式。

### E7：真实 Agent–OpenViking 整系统交互

任务级主评测采用 LoCoMo/OpenClaw 与 OpenViking 的 τ²-bench 适配，分别记录问答/任务延迟、记忆调用、任务完成和 Token。延迟为主要性能结果，正确率和完成率检查效果是否受到影响；τ² 的训练记忆生成、在线执行与评分分别计时。其记忆 adapter 的请求必须经过受测入口，不将其其他业务工具默认纳入 Argus 保护范围。下面保留 OpenClaw–OpenViking 的具体整链验收场景。

在 B2/B3a/B3b/B5 的适用配置上，用相同任务与模型预算配对运行：

| 场景 | 完成条件 |
|---|---|
| 首次完整任务 | 两端准入与凭据加载完成；真实 Gateway 经 mTLS 发起任务；OpenViking 捕获本轮标记并满足业务结果条件 |
| 会话写入与读回 | session/request ID、内容与读回结果一致，记录请求来自 Gateway 还是验证进程 |
| 读取/检索后的上下文使用 | Gateway 实际读取/检索并使用 OpenViking 上下文，产出预定义结果 |
| commit/archive | 提交接受、后台 task 完成、归档状态分别确认和计时 |
| 持续交互与更新 | 多轮/并发会话和双端轮换期间，核对任务结果、双方实际证书及连接代次 |
| 故障与恢复 | 在真实任务中注入 E1/E4 场景，核对拒绝位置、数据效果、任务状态和恢复读回 |

上下文使用任务可采用随机事实写入后查询。后续输入不直接包含答案，并排除本地历史或缓存；记录实际读取及上下文注入，配合移除相关上下文的控制组。模型答对与实际使用 OpenViking 的证据分别保存。

现有 [E2E 脚本](../../adapters/OpenClaw/scripts/verify_openclaw_plugin_e2e.sh)可复用真实会话、Gateway POST 审计、读回和归档检查。其部分读回/commit 由验证进程执行，且业务开始前已通过健康检查，因此需补 Gateway 上下文使用观测及外部冷启动计时。

输出首次可信任务、用户结果、归档完成的时间；任务正确率、受信任条件下完成率、任务 Goodput；每任务请求、重试、后台处理、token 和资源成本。

## 6. 指标与统计方法

### 6.1 指标口径

| 指标 | 定义 |
|---|---|
| Node 错误接受率 | 无效节点被接受次数 / 对应无效节点尝试数，并记录下游身份和业务结果 |
| 错误身份交付率 | 为不合格目标向配置的持钥组件交付可用 SVID 的次数 / 对应无效准入尝试数；CA 签发事件另记 |
| 错误后端执行率 | 违规请求被目标后端接受处理次数 / 对应违规请求数 |
| 非法数据交付 | 指定不合格接收点实际得到的记录/字节/测试秘密 |
| 合法误拒绝率 | 合法且依赖满足约定可用条件时，错误拒绝次数 / 合法尝试数 |
| 请求与任务时延 | 各自 P50/P95/P99、绝对差、相对开销及区间；启动、稳态、更新分开 |
| 请求/任务 Goodput | 单位时间内结果正确、满足信任/权限条件且在对应 SLO 内完成的数量 |
| 失效与恢复 | 触发到指定交互停止的观测窗口、残余数据、恢复时间、丢失/重复/未知任务 |
| 资源与接入成本 | CPU 时间、实际 PSS/cgroup 内存、连接/FD、网络/证据字节，以及代码/配置/步骤 |

身份事件、请求和任务采用不同分母。NGINX 接收正文与 OpenViking 后端执行分别记录。SVID 年龄、Node/Workload 证据年龄、策略版本和连接年龄分别记录。

### 6.2 重复、负载与判定

| 项目 | 初始预算 |
|---|---|
| 冷启动 | 每配置 30 次独立启动 |
| 较便宜的准入 | 每配置 100 次 |
| 稳定请求 | 10 个独立配对块；每轮 60 秒预热、至少 180 秒测量 |
| 随机故障 | 每配置 30 次独立事件 |

预实验与正式数据分开。根据预实验方差、业务 SLO 和有意义的差异/估计精度，冻结最终样本量、时长、矩阵和分析方法；上述次数不作为充分性保证。轮换及到期测试覆盖实际周期，加速 TTL 结果单列。

- 在同一硬件条件下配对运行，块内随机或平衡配置顺序，每轮恢复相同数据状态；记录 CPU/NUMA、资源限额、软件/镜像版本、RTT、缓存及 TLS 设置。
- 默认报告 95% 置信区间。请求分布按运行块做配对 bootstrap；任务按任务/共享会话聚类，避免把相关请求当成独立重复。高频场景约 10 万请求作为尾部采样起点，P99 结论仍取决于区间精度。
- 若检验优越性或不劣性，事前确定有业务意义的界值并按配对方差规划样本，目标功效 90%；若仅估计相对开销，可先以区间半宽 5 个百分点规划精度。数字属于本方案的统计设计，不是性能通过线。
- 超时、重试、拒绝、崩溃保留在成功率与 Goodput 统计内；成功请求延迟单列，未完成时间保留删失状态。仅剔除事前定义的观测无效样本并公开原因。
- 安全结果逐场景报告违规数/有效尝试数和合法控制；确定性负例的零违规不推导总体攻击概率。对主要多重检验预先定义检验族，探索性结果另标。
- 单机采用单调时钟，跨机记录同步误差或使用往返观察。各阶段 P99 不相加，未显著差异不作为等价结论。

质量参照 CCF A/B 系统与安全完整研究论文所强调的对照、充分证据和复现要求：[OSDI CFP](https://www.usenix.org/conference/osdi26/call-for-papers)、[DSN CFP](https://dsn2026.github.io/cfpapers.html)。

## 8. 执行顺序与交付

1. **准备与预实验**：锁定两端代码、插件包、镜像和 Node/Workload/Entry/policy 配置；实现适用基线与实验 profile；建立事件关联和业务 oracle；验证真实 Gateway→OpenViking 正例。
2. **安全与完整业务**：执行 E1、E4、E7，确认拒绝位置、实际业务结果、更新和恢复行为。
3. **正式测量**：预实验后冻结参数，执行 E2/E3/E5 及 E7 配对测量；通用性主张由 E6 支撑。
4. **汇总与复现**：从原始记录生成跨层安全表、启动/证明分解、请求与任务曲线、故障/恢复时间线、资源与接入结果，并在干净环境重建核心结果。

每次运行保存版本/环境、配置、数据摘要、随机种子、块编号、起止时间及完整失败记录。关联两端 Node/Workload 证据、实例、证书代次、Gateway run/session、HTTP request 与 OpenViking session/task；用 actor 区分 Gateway、后台服务和验证进程。

复现材料包含基线补丁、构建/部署配置、数据与故障生成、运行/分析/绘图脚本、预期输出、硬件需求及时间预算。实验凭据重新生成，真实私钥和业务秘密不入包。[Middleware Artifact 指南](https://middleware-conf.github.io/2026/calls/call-for-artifacts/)

正式运行前需补齐的具体项见[方案 Review](评估方案Review-CCF-AB-2026-09-07.md)。
