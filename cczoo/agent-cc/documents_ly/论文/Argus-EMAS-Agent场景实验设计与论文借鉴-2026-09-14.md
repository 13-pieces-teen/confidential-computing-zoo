## 1. 这组实验要回答什么

Agent 在多轮任务中会持续把上下文和中间产物交给外部服务，并根据返回结果决定下一步。Argus 的作用需要落实为可观察的任务行为：正常服务能否支持任务完成；接收实例不符合条件或发生变化时，敏感交付是否按规则停止；合法恢复后任务能否继续，以及为此付出多少时间和集成成本。

当前性能评价的主要假设是：Argus 的直接影响更可能表现为首次就绪、请求延迟、并发容量、吞吐及运行变化时的等待。任务正确率、完成率和 Token 用于检查这些影响是否传导到 Agent 效果，不预设 Argus 会改善模型能力，也不预设效果一定不变。正常负载性能与故障下的准入性质分别评价，Server 混合负载作为主要结果来源之一。

这些问题不要求威胁是 Agent 独有的，也不要求接收方一定是另一个自主 Agent。记忆、诊断、测试和核验程序都可以是 Agent Service。实验中的 Agent 必须实际运行模型—工具—反馈循环，后续行动能够依赖服务结果；单独的 HTTP 脚本和固定轨迹重放用于测量通信及机制成本，不能代替这一层证据。

将问题细化为以下互相关联的比较：

| 实验问题 | 固定什么、改变什么 | 支撑的论文内容 |
|---|---|---|
| Argus 对问答和 Server 性能有多大影响？ | 固定任务/数据、模型、资源、连接与负载条件，对比普通 OpenViking 和 Argus 路线，再分解 TDX、TLS、证明与身份成本 | C3 的问答延迟、Server 吞吐、尾延迟、并发容量与异常分析 |
| 准入机制怎样影响真实 Agent 任务？ | 固定 Agent、模型、任务、初始数据、业务权限和预算，只切换准入机制 | C1/C2 的机制是否影响实际敏感交付；C3 的任务结果 |
| 多轮任务中的实例变化会造成什么后果？ | 在可比较的任务阶段注入同一种变化，观察新连接、已有连接与在途输入 | C2 的失效关系，以及停止和恢复的代价 |
| 换 Agent 或服务后，哪些东西可以复用？ | 保持同等准入与交付要求，替换运行时或服务类型 | C3 的接入方法与适用范围 |

“让证明状态参与 Agent 后续执行抉择”保留为第 7 节的候选实验。主比较先固定错误处理策略，避免同时改变 Agent 决策方法和 Argus 机制，无法解释差异来自哪里。

## 2. 相关论文怎样评价，Argus 可以借鉴什么

这些论文的任务、威胁模型和部署环境不同。借鉴其判定方法，不把它们的安全结果或榜单分数直接转移给 Argus。

| 一手论文与位置 | 原论文的评价方法 | 对 Argus 的借鉴与边界 |
|---|---|---|
| [AppWorld](https://arxiv.org/html/2407.18901v1)，§2.2、§3.2 | 控制初始数据库和时间；用程序检查目标状态变化与非预期副作用，允许不同正确路径 | 为测试、核验服务建立可重置状态和结果断言。任务成功不依赖与唯一调用脚本匹配；其模拟应用本身不提供远程证明 |
| [ToolSandbox](https://arxiv.org/html/2408.04682v1)，§2.3、附录 A.6 | Milestone DAG 表达必要事件及部分先后关系；Minefield 表达禁止事件；另统计交互轮数 | 用“获得反馈—修订—复测”检查业务过程，用实际接收事件检查交付条件；无需强迫 Agent 走唯一轨迹 |
| [τ-bench](https://arxiv.org/html/2406.12045v1)，§3 | 终态与必要回答判定；pass^k 衡量重复运行全部成功的可靠性。论文也指出终态正确可能漏掉中途违反确认要求 | 对同一任务重复试验，将随机波动与机制效果分开；额外保留交付事件判定。pass^k 不等同于“尝试 k 次至少一次成功”的 pass@k |
| [LongMemEval 正式论文](https://proceedings.iclr.cc/paper_files/paper/2025/file/d813d324dbf0598bbdc9c8e79740ed01-Paper-Conference.pdf)，§3.1、§3.3–3.4 | 覆盖信息抽取、跨会话推理、时间推理、知识更新与拒答；分别评价最终回答和相关记忆召回 | 将 OpenViking 检索质量与 Agent 实际回答分开。使用其任务时固定版本、问题 ID 和历史构造方式，不能把完整历史或答案标签直接交给 Agent |
| [AgentDojo 正式论文](https://papers.nips.cc/paper_files/paper/2024/file/97091a5177d8dc64b1da8bf3e1f6fb54-Paper-Datasets_and_Benchmarks_Track.pdf)，§3.4、§4 | 用独立的 utility 与 security 判定，分别观察正常效用、受扰动效用和攻击结果 | 建立业务结果与交付条件两个判定器。其提示注入威胁与 Argus 的实例准入不同；获准程序返回恶意文本不由远程证明自动解决 |
| [Omega / Trusted AI Agents in the Cloud](https://arxiv.org/html/2512.05951v2#S9)，arXiv v2，§9 | 分开测量 WebArena 应用延迟、改造 MCPSecBench 安全任务及底层证明成本；不同实验有各自覆盖范围 | 借鉴“真实 Agent 任务＋机制分项测量”的结构。原文 §9.1 的应用延迟评价不等于任务成功率评价，§9 的原型也明确尚未实现 VMPL 隔离与可信启动；Argus 应按实际覆盖报告各实验 |

当前主要执行入口采用 OpenViking 已有的 **τ²-bench 与 LoCoMo/OpenClaw**，见第 3 节。上表仍提供评价方法参考：AgentDojo 与 τ-bench 帮助区分业务、安全和重复可靠性，Omega 帮助组织应用与底层成本；LongMemEval、AppWorld、ToolSandbox 对应后续扩展。上表的 τ-bench 是方法参考，不能将它与实际选用的 τ²-bench 混称为同一基准。

若采用公开基准子集，事先固定版本、抽样规则与任务 ID，逐项说明改动。修改任务内容、工具边界、数据或评价器后，称为改造子集或派生工作负载；仅借鉴评价原则时，明确称为自建任务。两者均不冒充原榜单成绩。

## 3. 两个任务 benchmark 与 Server 混合负载

本节按已核对的 OpenViking 提交 `192b813e7e3106680a5534e2d4c9bcf6d2390abd` 记录入口，执行时固定实际采用的源码、数据与配置。讨论中的“L-Eval／Local mode，带 OpenClaw”按上下文暂对应 **LoCoMo**：OpenViking 有明确的 `benchmark/locomo/openclaw` 入口。[L-Eval](https://github.com/OpenLMLab/LEval)是另一个长上下文基准，不与 LoCoMo 混用。

| 评价部分 | 复用的入口 | 主要观察 | 配套检查 |
|---|---|---|---|
| τ²-bench | `benchmark/tau2/llm` | 完整任务及分轮延迟、记忆调用延迟和次数、并发任务处理能力 | 完成率、Token、工具轮数、重试与超时 |
| LoCoMo + OpenClaw | `benchmark/locomo/openclaw` | 整次问答延迟、检索/读取延迟、不同并发下的完成速率 | 问答正确率、Token、实际记忆使用 |
| Server 混合负载 | `benchmark/custom/session_contention_benchmark.py` | QPS/请求吞吐、P50/P95/P99、错误率、后台处理速度、队列与饱和点 | 请求和后台任务结果、资源占用、实际身份与数据路径 |

### 3.1 τ²-bench：任务执行中的记忆调用

采用 OpenViking 已有的零售、航空任务适配。它用训练会话生成经验记忆，在首次用户输入及特定写操作之前调用记忆服务；任务模拟与评分由外部 τ²-bench 执行。固定训练语料及其生成的记忆快照、测试任务、模型、种子、重复次数和用户模拟器配置，比较相同任务通过普通 OpenViking 与 Argus 接入后的表现。[官方入口与配置说明](https://github.com/volcengine/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/benchmark/tau2/llm/README.md)

主要记录任务总耗时、各轮耗时、每次记忆调用及累计等待、并发任务数和完成速率。完成率、Token、调用次数和无效重试帮助解释时间变化：究竟是相同调用更慢，还是延迟和失败改变了后续执行。先在足够宽松且一致的预算下观察正常运行成本，再将固定时限作为敏感性实验。

该适配有自己的记忆注入与用户模拟器设置，应连同 τ²-bench 提交一并记录，结果称为 OpenViking 的 τ²-bench 适配评测。训练提取与在线执行分开计时；完整超时、失败和缺失结果保留在分母中，不照搬上游探索性汇总里排除超时单元的做法。此时 Argus 的受测边界首先是 Agent→OpenViking，不能据此声称 τ² 的全部业务工具也已经过证明。

### 3.2 LoCoMo + OpenClaw：问答与记忆访问成本

沿用官方的导入、OpenClaw 问答、评分与统计流程，并复用同一批对话和问题 ID。其 OpenClaw 入口真实向 Gateway 发送问答请求，记录 `elapsed_seconds`、轮数和 Token；与每题一次检索的其他 LoCoMo 入口区分，论文写明采用 `openclaw` 路径。[官方流程](https://github.com/volcengine/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/benchmark/locomo/README.md)、[问答计时源码](https://github.com/volcengine/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/benchmark/locomo/openclaw/eval.py)

主比较保持 OpenClaw、OpenViking、模型、上下文构造、提示和数据快照一致，只改变部署及可信通信条件。分别记录整次问答时间、Agent 侧记忆请求时间和 Server 处理时间；首次准入、冷索引/缓存、已就绪后的复用请求单列。原生记忆配置可作为记忆收益的参考，普通 OpenViking 与 Argus 的配对差异才用于估计 Argus 的影响。

任务正确率与 Token 是效果检查指标。查询不携带答案，隔离问题会话和会污染后续题目的新增记忆；共同采用同一导入及缓存规则。索引和记忆生成的差异不能混进在线通信开销，导入性能另做实验。若要声称任务效果基本保持，事先定义可接受差异并报告区间，而不把“不显著”当作等价。

### 3.3 Server 混合负载：主要性能评价

复用官方压测脚本的资源导入、`find/search/grep/glob`、session 写入、commit、任务轮询与观测流程。它已经输出请求明细、后台任务明细、分接口延迟及按窗口统计的结果。优先用持续复用的 SDK/HTTP 客户端测 Server；真实 CLI 子进程作为单独接入路径，避免将反复启动 CLI 的成本归入 Argus。[官方压测说明](https://github.com/volcengine/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/benchmark/custom/README.md)

| 负载条件 | 内容 | 要解释的现象 |
|---|---|---|
| 纯检索 | 固定数据规模与查询集合，变化并发 | 单次交互成本、吞吐增长与饱和点 |
| 纯写入/commit | 会话写入、资源导入及后台处理 | 请求接受速度与实际处理完成速度的差别 |
| 稳定读写混合 | 检索与写入/commit 同时进行 | 检索 P95/P99 是否因写入竞争而升高 |
| 写入或会话突发 | 正常查询期间集中产生写入或新会话 | 尾延迟、错误、积压及恢复到稳态所需时间 |
| 业务与准入混合 | 上述负载叠加新实例准入、重订阅或证书轮换 | 控制链成本是否影响在线业务；各事件分开测试 |

后续从两个任务 benchmark 的请求记录提取一组业务比例，再以读多写少、写入较多等条件做敏感性分析；每组固定请求比例、载荷与数据规模。安全拒绝、失效和实例变化另按第 4 节评价，正常压力实验先使用合法身份与获准实例。

现成脚本采用并发 worker，适合从 1/4/16/64 等候选档位观察闭环并发曲线。Server 变慢时这种发压方式也会自动降低请求速率，因此另按整系统 E3 设置相同绝对到达率的开放负载，记录计划发送、实际发送、完成和超时。发压端独立留出资源，避免把客户端排队或模型 API 限流误判成 Server 容量。

源码中的 `qps` 使用全部请求事件数除以窗口时长，含失败事件；原字段保留，同时补成功请求速率和后台任务完成速率。所有组采用相同测量窗口、连接池、重试与超时设置，并报告窗口结束时的未完成请求和任务。[压测调度及统计源码](https://github.com/volcengine/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/benchmark/custom/session_contention_benchmark.py)

Server 压测和 Agent 任务相互解释：前者定位容量与组件竞争，后者展示这些成本在真实任务中的影响。API 压测的并发客户端数、活跃会话数、Agent 任务并发、TDVM 数及服务实例数分别记录，不能互相替代。

## 4. 实验如何与 Argus 的实际机制对应

### 4.1 完整 Argus 路线的部署条件

在 B5 中，B 的实际业务程序通过可信启动器在约定 Intel TDX TDVM 内启动并登记；受信组件取得实例、镜像与配置属性，将绑定材料和新鲜挑战关联到 Quote；验证方核验 Quote、材料与批准政策，身份系统实施准入；通信入口与该业务实例保持受控关联。A 使用预期身份和认可的准入规则交付输入。其他比较组按第 4.2 节明确替换相应证明或身份机制，业务程序、数据和权限保持一致。

TDX Quote 为可信取得的材料提供绑定依据，不自行证明业务逻辑正确或程序永远不会泄漏。批准 Guest、启动器、取证与通信组件的信任条件应固定；所有比较使用相同业务授权和应用行为。实验可先固定共同认可的信任域，不把企业 A/B 的业务分工自动等同于跨身份域互认。

首次准入后有效依据可以复用，不预设每次工具调用都生成新 Quote。证明服务故障是否要求停止已有任务，取决于当时适用的有效期、租约与失效条件；将这些规则写进实验配置，不能事后按结果修改。

### 4.2 比较组与故障触发

延续原方案 B2、B3a、B3b、B5。B2 提供相同业务与通信路径的静态身份参照；B3a 引入已证明节点与较强原生工作负载检查；**B3b 在已证明节点上保持同等透明日志核验、实例属性核验、策略、凭据发布和失效联动，但不生成第二份 Workload Quote**；B5 为完整 Argus。优先比较 B3b 与 B5，并用原 B4 的单项消融解释入口或失效机制作用，避免只用弱身份基线证明优势。

2026-09-17 架构对齐：透明日志是可审计启动依据的组成部分，Rekor 为当前实现，OpenViking 经 TC API 形成受控启动记录。当前日志核验与 SPIRE 准入尚未接通，以下新增检查状态为 `proposed_not_run`。按目标架构比较 B3b/B5 时，两者固定日志确认、记录来源/包含核验、证据新鲜度与实例关联条件，仅改变额外 Workload Quote；缺少日志门禁的当前原型单列为阶段参照。比较同时报告日志关联所需的全部 Quote 数量、生成时点与节点重新证明成本，区分复用证据和新增采集。日志机制另与保留同等受信启动记录、实例检查及策略的配置比较，分别观察可审计性、实际身份交付和准入成本，不能把两项机制的收益混在一起。

性能评价同时使用原 B0/B1 的普通 VM 与 TDX 控制，以及相同 TDX、相同入口/业务权限下的 B2/B3b/B5。各配置独立运行同一任务集或同一到达负载，报告差异的绝对毫秒数、相对比例和置信区间；不将不同部署、模型或版本的官方结果直接作为配对基线。首次可信就绪与已经准入后的稳态交互分开，正常 SVID 轮换不计作重新生成 Quote。

受测 HTTP 客户端需要实际使用 Argus 身份与精确对端校验，入口再关联到经过可信启动和 Quote 核验的真实 OpenViking 实例。仅替换 URL，或只在普通后端前给代理做证明，不构成完整 Argus 组。τ² adapter、OpenClaw 插件和发压程序的 transport 适配分别记录，其余业务逻辑尽量一致。

| 条件 | 注入方式与合法配对控制 | 实际观察 |
|---|---|---|
| 正常任务 | 批准实例持续服务；正常 SVID 轮换作为控制 | 任务完成、误阻断、开销、Quote 与验证次数 |
| 首次准入错配 | 未批准镜像或配置；配对使用批准版本 | 请求在哪层被拒绝，敏感载荷是否到达入口及业务进程 |
| 启动记录与证明错配 | 缺失记录、来源/包含证明不符、另一节点或旧启动实例记录；合法同实例记录作为配对控制 | 是否获得目标身份，拒绝发生位置，敏感内容实际接收 |
| 日志确认或核验不可用 | 延迟提交或缺少所需证明；区分首次准入与仍有效的既有准入 | 不新授予缺少必要日志依据的身份，测等待/拒绝及首次可信就绪成本；既有连接按冻结的有效性规则判断 |
| 合法实例重启 | 同一批准版本产生新实例 | 旧依据停用、新实例重新准入、后续交付及任务恢复 |
| 不符合条件的替换 | 逻辑服务身份不变，目标改为未批准版本或配置 | 旧连接上的新输入是否流入替换实例，拒绝及检测传播时间 |
| 身份或凭据链失效 | 移除身份、Helper/Broker 不可用等适用事件 | 新连接、旧连接新请求、在途数据分别怎样变化 |
| 证明服务暂不可用 | 分开测试首次准入、更新准入与仍有效的既有依据 | 按事先规定的有效性规则判断继续或等待，记录可用性代价 |

真实 Agent 任务用外部调度器在指定业务事件后注入，例如首次 OpenViking 检索响应返回后、下一次记忆读取或写入请求发出前。触发点按各 benchmark 实际调用轨迹预先固定，不假定每个任务都有后续记忆调用；未到达触发点或故障后没有后续交付的试验单列，不能伪装成已检验后续交付阻断。另做持续请求的时间测量，取得真实停止窗口；这种机制测量与任务阶段触发回答不同问题。

固定模型版本、提示、工具、初始状态、最大步数、token/时间/重试预算和恢复规则，随机交错各比较组。相同任务与重复编号形成配对；真实 LLM 闭环用于评价任务，固定轨迹重放用于隔离机制成本，结果分别报告。

## 5. 业务结果与实际交付分别判定

### 5.1 两个判定器

**业务判定器**检查最终答案、测试结果和环境状态，必要时检查有部分先后关系的里程碑。记忆任务另外保留检索与上下文使用证据。确定性结论优先用程序断言；需要判断解释质量时使用固定、盲化的评分规则，并抽样人工核对，不能让 Agent 自报成功。

**交付判定器**关联调用方、通信入口与业务服务端的实收事件。使用合成敏感标记和已声明的敏感字段，记录 `run/task/session/tool_call/request`、实例与启动代次、证据/策略引用、身份/证书代次和连接标识。事件记录至少区分尝试发送、入口接收和目标程序接收；安全结论不依赖模型评分或单独的 HTTP 状态。

故障调度器与实收记录共同判断“接收时该实例是否满足条件”，不能只读取 Argus 自报的允许/拒绝。测试装置先以可控正例确认未准入实例若收到标记能够被检测。合成标记检测不覆盖任意改写后的语义泄漏；结论限定在测量的字段、接收边界和故障条件。停止窗口注明采样精度、时钟误差及在途请求，不能把未观测到事件写成瞬时零泄漏证明。

### 5.2 需要一起报告的指标

| 指标 | 定义与用途 |
|---|---|
| 业务任务完成率 | 正确完成的任务数／全部分配任务数；全部拒绝不计完成 |
| 满足交付条件的任务完成率 | 正确完成、未观测到交付违规且在约定预算内的任务数／全部分配任务数 |
| 实际违规交付 | 不符合条件的入口或业务实例实收的指定敏感请求、字段或字节；同时给出分母与观测覆盖 |
| 正确阻断与误阻断 | 应拒绝交付是否被阻止，仍满足条件的交付是否被错误阻止；与业务完成分列 |
| 停止与恢复 | 故障、最后实际交付、确认停止、新实例准入和首次合格业务交付之间的时间 |
| 任务与机制成本 | 完整任务延迟、模型 token/调用、重试、等待、Quote/验证次数；拆分准入、通信和应用处理成本 |
| 重复可靠性 | 同一任务多次运行的完成分布，必要时报告 pass^k；同时给出重复次数及估计方法 |
| 接入成本 | 应用/适配器/核心非生成代码改动、配置项、维护组件、部署步骤及作者工时记录 |

结果展示至少区分四类：完成且满足交付条件、完成但发生违规、未完成但未发生违规、未完成且发生违规。“未完成但未违规”还应区分正确拒绝、误阻断和 Agent 业务错误。

正常可完成、发生变化后仍可合法恢复、预算内所有路径都不再获准的任务分开报告。最后一类中拒绝可能是正确行为，但不能提高任务完成率。Server 延迟报告 P50/P95/P99；Agent 问答/任务报告样本量支持的分位数，并同时给出失败、超时和预算耗尽，避免只统计成功任务掩盖代价。费用覆盖所有重试与失败尝试；样本不足时不将不稳定的任务 P99 作为主要结论。

先用独立 pilot 估计难度、方差和成本，再冻结正式样本与重复次数，不按已看到的机制胜负筛题。按任务或独立会话做配对分析与 95% 置信区间；共享同一故障事件的多次请求不能当作相互独立样本。复用成本的对照也允许使用共同库，不能要求基线从头实现全部功能；作者工时只支持案例记录。

### 5.3 Server 性能的核心指标与计时边界

| 指标 | 统一口径 | 用来判断什么 |
|---|---|---|
| 发出/接收请求率 | 每秒计划发出、实际发出、Server 实收请求数分别统计 | 两组承受的压力是否一致，发压端是否成为瓶颈 |
| 请求吞吐与成功吞吐 | 测量窗口内完成请求数/秒、成功请求数/秒分别报告；检索子集可记 QPS，全接口记 req/s | 处理速度，避免快速错误或拒绝使总 QPS 虚高 |
| P50/P95/P99 | 按接口、负载阶段及结果类型统计客户端请求延迟，并保留服务端处理分布 | 中位开销、尾延迟与异常集中在哪条路径；不对不同接口分位数取平均 |
| SLO 有效吞吐 | 正确完成且满足对应延迟目标的请求数/秒；同一目标应用于所有比较组 | 在可接受服务质量下的容量，而非只追求峰值 |
| 错误率与异常 | 超时、连接/TLS 错误、5xx、限流、业务错误、无结果及后台失败分别记录 | 区分性能退化、上游问题和应用行为；安全实验中的预期拒绝另列 |
| 异步处理吞吐 | 成功完成的资源导入数、commit 数或处理字节数/秒，保留失败与未完成量 | `accepted` 之后实际处理了多少；不能以提交 QPS 替代完成吞吐 |
| 排队与恢复 | 待处理/处理中任务数、等待时间、积压增长斜率、停止加压后排空时间 | 是否真正处于可持续稳态，突发后能否恢复 |
| 并发容量与资源 | 活跃请求/会话/任务数、CPU、内存、网络/磁盘及控制链资源 | 饱和点在哪里，Argus 与业务组件各消耗多少资源 |

异步任务吞吐同时给出稳态固定窗口与整批完成时间；若窗口内积压持续增长，就不能把当时的提交速率称为可持续处理能力。排空阶段单列，仍未完成的任务明确计数。载荷大小变化时同时报告 bytes/s 或文档大小分布。

| 时间范围 | 起点与终点 |
|---|---|
| 用户问答/任务 | Agent 接受任务到最终回答或终止；包含实际重试与等待 |
| 工具/记忆请求 | 调用方发起请求到完整读取响应，覆盖连接、入口和服务等待 |
| Server 内部 | 请求进入服务处理到响应完成；另记排队、检索、模型调用等阶段 |
| 首次可信就绪 | 明确冷启动范围，从启动/准入开始到首次成功的合格业务请求 |
| commit/导入完成 | 客户端提交开始到后台任务终态；另测目标记忆首次可检索的时间 |

端到端时间直接测量；阶段可能嵌套或并行，不能把阶段 P99 相加。OpenViking 已提供 HTTP、检索、模型、资源处理与队列相关指标，可与客户端和 Argus 控制链计时关联；以实际固定版本能导出的指标为准。[官方 Metrics 说明](https://docs.openviking.ai/en/concepts/12-metrics)

## 7. 候选实验继续保留，但不改变主线

**证明状态参与后续执行抉择。** 在主机制实验之外，固定证明机制、可选获准服务及预算，比较通用错误、包含同样事实的自然语言反馈、结构化状态，以及获得同等信息的规则控制器。观察正确等待、受约束替代、无效重试、合格完成和额外模型成本。底层准入规则保持一致，Agent 的替代选择不能放宽数据条件；并非任何业务都有可替代 B 的资源，需明确哪些任务允许等待、替代或只能报告未完成。

**敏感交付时按需核验。** 比较首次准入后复用、按有效期/事件更新和敏感交付门禁，分别计数检查既有结论、验证证据和生成新 Quote。业务规则事先标注敏感输入与返回数据，不要求模型自行决定安全门槛。该能力仍为候选设计，不能写成当前已实现；不以“每次调用生成 Quote”作为唯一成本基线。

这两项的意义是发现框架还可以怎样被 Agent 使用。无论结果是否正向，原论文仍以分层证明、实例—身份—入口关联及真实 TDX 评价为基础；贡献是否成立及其强度，由实际比较决定。

其他讨论过的方向继续保留，当前两个 benchmark 的选择不要求删除这些想法：

| 候选方向 | 可继续研究的问题 |
|---|---|
| Bosch 式诊断与复测 | 固定获准测试程序，Agent 提交结构化复现输入或配置，根据反馈修订并复测；用隐藏回归用例判定。实例变化可发生在两轮之间。完整场景见 [Intro](./Argus-EMAS-Intro-跨企业可信服务协作-2026-09-12.md) |
| LongMemEval、RAG 与记忆更新 | 不同数据、检索粒度和上下文规模下的性能，以及从写入到后续任务实际用上记忆的时间 |
| 第二运行时及共享服务 | 利用官方已有 Hermes/Claude Code 评测，或接入 [LangGraph Agent](https://docs.langchain.com/oss/python/langgraph/workflows-agents)，研究接入复用、共享服务与独立部署的资源/性能取舍 |
| 银行核验、AppWorld 和真实 A2A | 以合成核验状态或 [AppWorld](https://github.com/StonyBrookNLP/appworld)可执行任务拓展服务类型；B 若是自主 Agent，再覆盖其实际运行时与下游路径 |
| 性能对执行选择的影响 | 固定时间预算，研究等待、重试、减少检索或放弃复查怎样影响任务结果 |

复用比较在各运行时内部配对固定任务与机制，并按实际完成的组合报告；普通 Go/Python 请求脚本只支持协议与通信结论，不能代替真实 Agent。第二服务或 A2A 接收方同样需要可信启动、Quote 与真实入口关联，不能只保护外层代理。

## 8. 推进顺序与论文中应呈现的证据

1. **复用两个 benchmark 的正常配置。** 固定 τ²-bench、LoCoMo/OpenClaw、OpenViking 及模型版本、任务和数据快照；确认实际记忆使用，解决相关闭环缺项。
2. **建立 Server 性能比较。** 在普通 OpenViking 与 Argus 路线上运行纯读、写入/commit、稳定混合和突发负载，测吞吐、分位延迟、错误与后台完成；该项可独立于模型任务评测推进。
3. **关联任务效果与组件成本。** 对两个任务 benchmark 做配对运行，连接问答/任务时间、Server 请求时间和 Argus 准入时间；用同等 VM/TDX/TLS 配置与 B3b 等比较解释来源。
4. **继续扩展研究问题。** 按原 E1/E4/E5 检验运行变化和控制链竞争；第二运行时、业务场景、证明反馈及按需核验继续作为候选，依据结果选择深入方向。

性能部分优先呈现两个任务 benchmark 的延迟与效果对照表、Server“并发/到达率—成功吞吐—P95/P99”曲线、纯检索与混合负载对照，以及错误和后台积压时间线。首个可信请求与稳态请求分开展示。准入与实例变化的安全证据按原研究问题保留，接入矩阵依据实际完成范围呈现。

这些证据要说明的是：Argus 的执行依据在真实 Agent 任务中如何影响交付、可用性与接入方式。若强基线也能保持相同条件，应如实报告，并进一步解释额外 Quote、独立验证方需求或集成方法的成本和适用范围。
