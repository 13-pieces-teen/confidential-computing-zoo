# Agent-CC 框架价值与核心贡献研究

研究日期：2026-09-06。本文是研究方向比较，不是已实现架构或验收报告；候选创新均有待进一步文献比较、反例和实验验证。

当前源码 HEAD：`467ad8a`。当前文档和验证记录表明：Node 已有历史验证；当前升级版本仍需复验；Workload 已有实现和本地软件/集成测试，真实 TDX 全链路仍待验收。当前路径以单个 OpenViking 服务实例为中心，不能把旧双 Broker 文档、规划中的联邦或周期重新证明当成已实现能力。

## 1. 框架首先提供什么价值

一个合适的框架定位是：让独立运营的 Agent、上下文服务和工具，能够核验对方的身份与执行条件，再决定是否共同完成任务、交换数据或交付密钥。

这需要明确区分数据所有者、Agent/模型提供者、服务提供者、基础设施运营方、身份签发方、证明验证方和策略批准方。它们可以由同一组织承担，也可以分属不同组织。机密计算减少对部分基础设施操作的信任，但不会消除所有信任根。

| 参与方 | 当前业务障碍 | 框架可能提供的价值 | 需要证据支持的效果 |
|---|---|---|---|
| 数据所有者 | 想使用第三方 Agent，又不愿把原始上下文交给任意运行环境 | 按自己认可的身份、代码和执行环境条件交付数据 | 条件不满足时确实阻止交付；满足条件时正常任务可完成 |
| Agent/工具提供者 | 希望跨企业部署，同时保护代码、配置和运行状态 | 可携带的服务身份及运行证据；在约定边界内保护资产 | 不同客户复用多少接入工作；资产在哪些组件可见 |
| 上下文服务提供者 | 多租户、多云 Agent 共同访问同一服务，认证方式和证明要求各异 | 标准身份入口与明确的证明准入规则 | 弱证据、错误实例、错误租户等条件能否区分和拒绝 |
| 企业平台团队 | 每个 Agent 框架和工具都重复实现凭证、证明、代理与失败处理 | 复用 SPIFFE/SPIRE 和统一的证明集成接口 | 接入修改量、配置错误率、排障成本、可信启动时间 |
| 跨组织协作方 | 出事后难以确认谁根据什么条件交付了数据 | 可核验的准入、变更和交付历史 | 能否发现遗漏、过期依据和相互矛盾的历史 |

上述是价值假设，不是已测得的成本下降或市场需求结论。

技术职责应保持清楚：TEE 保护约定的执行与密钥边界；Node/Workload 证明提供可观测状态证据；验证方按参考值和策略评估；SPIRE 根据准入规则签发 SVID；SPIFFE 支持身份表达、认证和跨域互操作；授权方决定具体操作；透明机制支持声明和历史核验。

SPIFFE Federation 使外域 SVID 可以验证，不自动使双方证明政策等价。SVID 本身不是硬件 Quote。多个同 SPIFFE ID 的副本可以完全合法。同一 TDVM 内的多个容器，也不会因此获得相互独立的硬件隔离。

依据：[SPIFFE Concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/)、[Federation](https://spiffe.io/docs/latest/architecture/federation/readme/)、[RATS RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html)。

## 2. 文献把哪些直观贡献变成了已有工作

|---|---|---|
| [Multi-Platform and Vault-Free Attestation of Confidential VMs，LADC 2024](https://doi.org/10.1145/3697090.3698036) | TDX SPIRE NodeAttestor，多 TEE/多云，身份与密钥交付 | TDX + SPIFFE + 多云不能单独作为新贡献 |
| [HIEST，CyResTrust/ARES 2026](https://link.springer.com/chapter/10.1007/978-3-032-35576-8_13) | 从 TCB、解释器到应用及输入的分层证明，限制已证明环境被用于其他应用 | Node 到应用实例的延伸并非空白；本轮核实到出版方摘要，不能据此断言未提供某种功能 |
| [Full Trust Alchemist，Middleware 2025](https://www.comsys.rwth-aachen.de/publication/2025/2025_galanou_trust-alchemist/) | 按验证方需要提供工作负载运行证据，覆盖动态状态和策略；强调证据生成组件与密钥保护 | 运行时配置证明、选择性证据和密钥绑定已有强近邻；深层细节来自作者 PDF 索引，仍需完整复核 |
| [Omega / Trusted AI Agents in the Cloud](https://arxiv.org/html/2512.05951v2) | 机密 Agent 平台、差分证明、动态 Agent、工具策略、日志与状态保护 | 多主体证明、增量证明和可核验 Agent 日志都不能直接作为新颖性；需要比较独立运营域下的差异 |
| [Grimlock，AgenticOS Workshop 2026](https://arxiv.org/html/2605.27488v2) | 强制代理、通道绑定证明、跨云 Agent 和委托权限的愿景设计 | Guard + 证明 + scope token 已有；完整实现也仍需新性质或新发现支撑 |
| [aDNS，USENIX Security 2025](https://www.usenix.org/conference/usenixsecurity25/presentation/delignat-lavaud) | 域名、证明、域策略、证书和透明日志的关联 | 把 DNS 换成 SPIFFE 不足以成为贡献 |
| [Apple PCC](https://security.apple.com/documentation/private-cloud-compute/verifiabletransparency) | 可核验软件发布和运行证明支撑请求交付 | 证明匹配已批准发布版本后交付密钥也已有成熟设计 |
| [SCITT，RFC 9943](https://www.ietf.org/ietf-ftp/rfc/rfc9943.html) | 签名声明、透明服务、可核验回执 | 便携回执和追加日志可以复用标准；入日志不保证声明真实、执行成功或事件完整 |

补充比较对象：[Certifier Framework](https://github.com/ccc-certifier-framework/certifier-framework-for-confidential-computing) 已提供多平台的策略驱动信任管理；[AgenTEE](https://arxiv.org/html/2604.18231v2) 已有多个资产所有者分别证明隔离环境后交付资产；[Atoma 论文](https://arxiv.org/abs/2410.13752) 探索不受同一运营方控制的机密 AI 服务。不能将这些基本商业场景称作首次提出。

## 3. 七个候选方向

### A. 被选择的工具与实际执行实例如何可靠对应

场景：Agent 根据目录或 MCP 描述选择服务；请求经过代理、负载均衡和后端重启后，由另一实例实际处理。同一逻辑身份仍然有效。

研究问题：在独立管理域中，如何关联描述版本、逻辑 SPIFFE 身份、证明结果、实际实例、密钥使用者和数据通道，并在关系变化后使旧依据失效？

SPIFFE 为逻辑工作负载提供稳定身份；RA 给出具体执行条件；TEE 保护取证、持钥与强制转发路径。身份与实例不能简单合并，同一服务允许合法扩容。

候选贡献是跨域关系变化下的可核验对应性质、协议和反例，而不是给 descriptor 增加哈希。当前实际 PID、配置、实例与 Helper/NGINX 边界最适合成为这条线的实现基础。

反证：若给 Omega、Grimlock 或常规代理配置完整的后端身份和证据绑定即可排除全部反例，那么主要是集成工程。

### B. Agent 生成新工具后，新代码凭什么取得身份和权限

场景：Agent 临时生成 Python 工具或创建子 Agent。该产物没有事先批准的镜像哈希，但需要访问私有上下文服务。

研究问题：能否证明一个受批准的生成、检查、隔离执行与身份签发路径，使新产物取得可追踪、权限受限的身份，而不用逐个预登记？

安全依据必须来自可信验证器、隔离机制或可检查约束；不能仅因为父 Agent 自报安全，或者程序运行在 TEE 内，就授予数据访问权限。运行代码的身份、行为限制和具体访问权限应分别表达。

已有 [Uranus](https://www.cs.hku.hk/~heming/papers/asiaccs20-uranus.pdf) 研究动态字节码证明，[Deflection](https://pmc.ncbi.nlm.nih.gov/articles/PMC9343090/) 研究受保护的加载/验证与代码约束。因此候选差异应落在任务生成产物的可信准入、跨域身份和权限继承，而不是动态代码度量。

反证：若只是对新代码计算摘要后发证，不能建立行为保证；若完全依赖现成沙箱，还须说明身份机制新增了什么跨域保证。

这是较有 Agent 特征、也更费研究投入的支线。

### C. 跨域准入政策变化时，旧身份还能支持哪些交互

场景：服务保持相同 SPIFFE ID，但准入策略、镜像批准范围或可信依赖发生变化；调用方仍持有旧证明或旧日志回执。

研究问题：如何明确策略版本、证明结论、SVID、长连接和业务动作的有效性关系？多个域独立更新时，哪些交互可以继续，哪些必须等待或拒绝？

透明日志可以连接批准、评估、身份签发及交付依据，但政策哈希不等于政策当前性。需要定义可信时间、检查点、失效传播、离线容忍和更新窗口。

候选贡献是跨域变化过程中的时序性质与机制，以及安全和可用性的实测代价。必须正面对比 aDNS、PCC、CCF 和运行时证明方案；缩短证书 TTL 不足以成为贡献。

### D. Agent 分叉、恢复和迁移时，身份及可信状态如何继承

场景：一个 Agent 因故障迁移到另一云，或被合法复制为多个推理分支。旧实例可能尚未退出，旧上下文和旧授权也可能继续存在。

研究问题：哪些状态允许分叉，哪些任务资源要求单一有效执行者？如何在保留逻辑身份的同时，核验恢复状态、实例代次和委托关系？

RA 判断新环境；SPIFFE 延续服务身份；外部状态、见证或日志支持历史和失效判断。不能把同 ID 多副本一律当攻击，也不能认为 TEE 自动提供所有反回滚性质。

Omega 已有防回滚状态，TEE 状态连续性也有大量研究。候选差异需要独立域、跨服务状态和合法分支的组合语义。当前项目积累可复用，但跨度较大，适合远期。

### E. 以可验证信任条件约束 Agent、工具和执行位置选择

场景：同一任务可以远程调用工具、把工具部署到数据附近、先提取可分享信息再委托，或改用其他模型服务。

研究问题：如何在身份、TEE/证明政策、数据可披露范围、任务质量、成本和时延之间选择可行协作方案？新工具加入、证明失效或云资源变化后，如何调整方案？

SPIFFE 使计划中选择的主体对应实际连接对象；RA 提供可核验的可行性条件；TEE 使某些原本不允许的数据处理位置成为可行选项。证明条件应是明确约束，不应随意压缩成一个能被价格或准确率抵消的“信任分数”。

候选贡献包括受信任条件约束的决策问题、规划/分配方法以及安全与任务效用的联合评测。公平基线必须包含“先筛掉不合格工具，再运行普通规划器”，以及动态更新后的强基线。

反证：静态过滤就能达到同样效果时，不存在新的规划贡献。证明后运行的程序也不因此获得任务正确率保证。

这是更直接适合 AI/Agent 主会的问题，但应当由真实约束冲突推动，不能只加入一个规划模块。

### F. 对 Agent 工作流的证明覆盖和信任失配做系统性评测

场景：任务成功、TLS 成功、Quote 验证成功，但隐私数据实际经过了没有被相应证据覆盖的代理、模型 API 或后端。

研究问题：如何定义可检验的证明覆盖范围，区分“有安全组件”与“实际执行满足声明的信任条件”？

可以研究受控反例集、检查方法和可复现实验环境。覆盖身份正确而证明条件过弱、证据和通道错配、动态后端替换、政策陈旧、共享服务扇入、下游新增、失败重试等。

若只是若干单元测试，它是验证工程；若能系统发现现有 Agent/CC 框架中共同存在的错误模式，并提供可迁移的检测或评测方法，可能独立形成研究贡献。

不能用预先标好的“坏节点”代替真实对抗；也不能将超出方案威胁模型的攻击算成其失败。基础设施攻击与 Prompt Injection 应分别报告。

### G. 商业机密下的选择性运行证明与审计

场景：客户要求证明政策执行，供应商不愿公开模型、Prompt、全部工具配置和客户关系。

研究问题：能否只披露决策需要的属性，仍支持跨域身份认可、策略变化核验和针对性历史分叉检测？

Full Trust Alchemist 已有验证方特定证据，SCITT 支持敏感载荷处理，CCF 有私密交易。加密日志和字段哈希不能单独构成创新，也不自动解决低熵内容枚举、时序和关系泄漏。

要独立成文，需要明确泄漏模型和可核验性质，密码学及实现负担较大，当前作为远期选项。

## 4. 如何组合成一篇论文

### 方案一：保留现有框架积累，聚焦跨域可信服务组合

以 A 为主问题，C 为变化与失效语义，透明记录支撑核验；F 为研究评测。

候选贡献表达：

1. 定义跨独立身份域中，逻辑服务身份、实际执行实例、证明政策与数据交付之间需要保持的安全性质。
2. 设计保留 SPIFFE 互操作性的关联与更新机制，让调用方按自己的条件接受证据，并拒绝过期或错配的依赖关系。
3. 通过动态工具发现、代理后端变化、跨域策略更新和共享服务场景，验证性质并测量成本与可用性。

这里的 1–3 是拟开展的研究，不是当前已有成果。它更自然地面向系统、安全及 Agent 基础设施研究。使用 Agent 负载本身不足以保证 AI 主会相关性。

### 方案二：以 AI/Agent 投稿为优先，聚焦可信条件下的协作决策

以 E 为研究问题，A 提供可执行的身份/证明约束，不将所有框架功能列为贡献。

候选贡献表达：

1. 定义具有动态能力、执行位置、证据有效期和数据披露约束的多 Agent 任务分配问题。
2. 设计能够利用可复用证明、选择协作路径并响应条件变化的决策方法；安全条件与性能目标分别处理。
3. 与静态过滤、固定部署、常规重规划和强动态基线比较，在相同模型及预算下测量任务质量、完成率、数据移动和证明成本。

其难点是先证明这是一个超出过滤规则的决策问题。如果做不到，应回到方案一。

### 方案三：大胆支线——生成式工具的可信准入

围绕 B 单独形成论文：任务产生新程序，可信验证/执行机制决定其可获得的受限身份，跨域服务据此授权。需要明确可保证的程序行为和验证依据，不能宣称 TEE 能验证任意生成代码安全。

## 5. 框架贡献与论文贡献分别如何判断

框架可以因统一接入、明确边界、可运行部署和失败处理而有价值，即使其中多数原语都已有研究。

论文则需要至少一项可检验的新结果：新的问题及安全性质、解决它的协议/算法、对现有方案的系统性新发现，或在相同保证下显著改变成本和适用范围的系统设计。

一个可用于自检的候选性质是：每次被允许的跨域交互，其身份、实际执行主体、证明政策、有效时间和声明的调用关系，应对应同一份可核验的准入依据；相关条件发生不被政策允许的变化后，旧依据不能继续放行新的交互。

它仍可能与既有协议重叠。需要找到实际反例和准确威胁模型，才能决定是否值得研究，不能仅靠写出这句话声明新颖性。

研究选择的关键反证：

- 完整配置现有方法即可消除全部反例：主要是集成价值。
- 静态筛选加普通规划器已达到同等效果：没有新的 AI 规划贡献。
- 只把生成程序度量后发证：缺少可信准入依据。
- 只把证明上传日志：缺少对实际准入与交付的约束。
- 只比较正常完成率，未测越权、误拒绝和证据成本：不足以判断框架收益。

## 6. 本轮优先判断

优先深查 A + C，因为它最能复用当前实际服务实例、Helper/NGINX 持钥边界、SPIRE 身份交付和失效处理。

若以 AI/Agent 主会为优先，进一步论证 E 是否存在真正的决策难点。B 是更大胆的 Agent 原生支线；D、G 暂留为远期。F 应从一开始支撑判断，有足够系统性发现时再考虑独立成文。

不建议把七个方向同时实现。当前先完成各候选方向的问题定义、最强近邻和反例比较，比增加更多功能更能决定论文路线。
