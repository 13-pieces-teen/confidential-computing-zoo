# Argus：论文 revision 1806 后的实现与实验取舍

2026-10-02，依据论文整体审计与作者确认。正式运行前固定源码、构建产物、策略、任务协议和证据清单；本文件不提供实验结果。

## 部署边界

服务端管理接口仅供受信管理员使用。Argus 本轮不新增面向不可信部署者的管理平台或独立部署模式，也不把恶意部署者可操作任意 Docker 接口作为默认威胁。容器启动、服务替换和重建由合法运维或故障触发；云宿主、外部网络和外部存储仍属于声明的不可信环境。

需要验收的实际前提是：管理 API、Docktap 和真实 Docker socket 对普通业务进程及外部客户端不可达。仅有一个“仅管理员使用”的约定不能替代实际权限、父目录、挂载、网络和端点访问验证。通用调试接口只属于管理域，不算面向 Agent 的业务接口。不要为了论文实验虚构一个现实部署中不存在的受限部署角色。

管理员也须遵守受支持的记录路径。本轮操作意图覆盖 `create/start/stop/rm`，不因此获得对任意 Docker 命令的完整审计保证。直接访问真实 Docker 或使用尚未覆盖的变更入口应作为超出该记录协议的管理操作明确列出；不能把可信管理员假设写成所有变更入口已经受技术强制约束。

在此范围内，受控记录仍有意义：即使操作由可信管理员发起，进程退出、网络中断和恢复也可能造成实际操作与可验证历史不一致。管理员受信不等于软件不会在中间步骤崩溃。

## 当前优先工作

1. 在 Docker 生命周期操作之前持久记录待决意图，保存操作结果并恢复后续记录提交；未知结果不自动重放操作。未确认的真实变更不能被新准入当作完整历史。
2. 首次披露、发送和应用读取分别记录。故障前释放、故障后才读取的输入，不得混入故障后首次释放的新事实。
3. 增加一个固定工作项的正常读写、故障与合法恢复切片。使用真实 Agent 工具和私有记忆，保持同一业务工作项和已确认状态的依赖；不要求恢复同一个模型推理进程。
4. 验证已有身份与代理控制的状态转移，区分凭据轮换、新订阅和替换实例准入。跨组件准入代次、同步关闭门禁及代理自动恢复属于独立实现项，未完成前不写为已经保证。

## E1–E5 的用途

| 实验 | 核心问题 | 解释条件 |
|---|---|---|
| E1 | 当前实例与历史政策如何共同决定准入 | 合法操作、外部证据攻击和管理员故障注入分别报告。先证明真实可达差异，再决定 current-facts-only 消融；共同本地拒绝不是历史独立收益。 |
| E2 | 失效后的实际读取和新增披露 | 根据实际释放时刻与应用读取判定；区分监督失效和实例资格不合格。缺资格证据保留 UNKNOWN。 |
| E3 | 复用与合法恢复是否遵守实例边界 | 同订阅 SVID 更新、新订阅和新实例分开计数；就绪、首次业务成功和任务完成分别记录。 |
| E4 | 准入和停止访问如何影响持续任务 | 固定私有工作项、真实 memory_store/recall、跨中断状态依赖。LoCoMo 只读 QA 保留为召回与接入质量的辅助检查。 |
| E5 | 信任建立和持续使用的成本 | 首次准入、历史长度、无关并发变化、新建／复用连接、正常任务与恢复成本分开。 |

主要比较仍是 Full 与保留同等本地控制的 native SPIRE。no-watchdog/no-close 用于解释停止机制，静态 mTLS 用作成本参照，不必把每个消融复制到全部 Agent 任务。没有复现的每调用租约或每连接证明不得写成已完成基线。

## 小型 Agent 任务的验收原则

- 一个稳定工作项，输入事实按固定时间表逐步释放；记录实际交给 Agent 的时刻，不能只记录计划时间。
- 正常阶段确认一次持久写入及其回读；恢复阶段从已确认状态继续，保留所有已经确认的有效更新。
- 故障期若写入结果不明，查询原 task/session/operation ID；未知 POST 不自动重发。未解决的必要状态不得被最终成功掩盖。
- 新 OpenClaw 会话可以继续同一业务工作项，但不能称为恢复同一推理进程。模型回答、工具调用、应用读取、持久提交和任务正确性分别验证。
- 报告全部计划步骤。模型未调用、超时、明确拒绝、未知和正确完成分别保留；没有实际调用不能算作安全拦截成功。
- 单客户端故障与共享服务故障分开；其他客户端的影响要结合真实共享依赖解释。

## 论文第四节的表述边界

准入条件应解释“谁凭什么获准接收”，运行控制应解释“该依据如何约束入口、何时结束”。记录持久化修复不是全局回滚保护；未决历史阻止新准入，也不自动等于已经停止旧连接。主动关闭仍要由原有目标检查、监督和代理控制实现并独立测量。

硬件 Quote 认证报告字段，事件语义依赖受信记录路径。完整历史需要同时处理实际操作到记录的窗口以及记录到硬件度量的恢复；没有实现的 RTMR 崩溃恢复、全局单实例、持续政策撤销和无延迟关闭均不扩写为已有保证。

第四节建议按以下因果顺序组织：

1. **部署与信任边界**：管理员、客户机运行时、SPIRE/验证设施与业务进程各自能做什么；给出代理和实例分离的实际部署图。
2. **实例准入的依据**：当前实例标识、批准策略与其关联的启动历史；解释硬件认证哪些值、记录路径保证哪些语义。
3. **操作与历史的一致性**：转发前记录意图，结果持久化后恢复提交，实际确认前维持新准入门禁；分别说明已知与未知操作的恢复。
4. **身份到接收路径的绑定**：以实际获准实例约束代理后端；凭据正常更新不等于实例重新准入。
5. **持续使用与合法恢复**：监督和目标检查触发停止，替换实例重新准入后恢复；明确异步停止窗口、未知状态和已有连接的处理范围。

这条顺序从“依据是什么”推进到“如何维持、在哪里执行、失效后怎么办”，避免把产品组件列表当作设计论证。Helper 仍为具体语言/部署的适配实现，不单列为研究贡献。

真实 TDX、部署权限、进程崩溃、NGINX 最后读取、模型任务及跨机性能继续为 **NOT_RUN**，直到相应原始证据齐全。本地 fixture 和单元测试不能填作这些结果。
